## Устройство программы (офлайн-версия, рабочая)
- `LIVARO.html` — точка входа (ярлык «LIVARO — учёт» на рабочем столе). Подключает `app/styles.css`, `app/vendor/html2canvas.min.js`, `app/vendor/xlsx.full.min.js`, `app/catalog-1c.js` (321 товар из 1С), `app/app.js` (вся логика, ~2500 строк).
- SPA на чистом JS (ES2017+), hash-роутинг `#/name/args`. `VIEWS[name]` возвращает HTML-строку. События делегируются через атрибуты: `data-act` → объект `ACT` (click), `data-ch` → `CH` (change), `data-in` → `IN` (input).
- Данные хранятся в **localStorage `livaro_db_v1`** (есть миграция из `livaro_trial_v1`; при загрузке недостающие поля добиваются по умолчанию). **Ключ не менять без миграции, данные пользователя не терять.**
- Объект DB: `cat` (дерево `{n, ch, it:[[name, price|null, pack?]], open, pack?}`), `clients` (opening: + на балансе / − долг), `orders` (status ordered/shipped/cancelled, shipDate, shippedAt, groups `[{t, items:[{n,q,p}]}]`, total), `payments` (method cash/transfer/driver/goods, status received/pending, alloc `[{orderId, amount}]`, atShip, goods `{what,qty,unit,price,stock}`, note), `templates`, `trash` (kind order/client/payment/item/folder/template/inst), `installments`, `instNo`, `stockMoves` (in/adj), `cart {groups, cur, editId}`, `nextNo`, `settings` (deepList, asst, labelFmt, oddDoor, invShow all/tracked/stock, invPlan, invBreak, invFolders — пути папок бланка, null = все, invMatrix — бланк «цвета колонками», по умолчанию true), `lastBackup`.
- **Баланс** = opening + полученные оплаты − отгруженные заказы. `payMap()` распределяет деньги по накладным: явно через alloc, остальное FIFO из пула с подписью источника («с баланса», «перевод»). Старый долг закрывается первым.
- **Заказ:** Оформлен (на баланс не влияет) → «Отгрузить» (дата и оплата при отгрузке) → Отгружен (списывает с баланса, печать «Накладная») → «Отменить отгрузку» (удаляет оплаты atShip). Отменён остаётся в журнале.
- **Склад** вычисляется: приходы и поправки минус отгрузки и рассрочки ПОСЛЕ первого движения товара. Резерв = оформленные заказы.
- **Автокопия:** `showDirectoryPicker`, handle хранится в IndexedDB `livaro/kv/backupDir`. Файлы `LIVARO ГГГГ-ММ-ДД.json` (30 дней) и `LIVARO последняя копия.json`.
- **WhatsApp:** html2canvas → PNG → `navigator.share({files})`. Запасной путь: буфер обмена и `wa.me/<телефон>` без текста (нужна именно картинка накладной).
- **Печать:** A4 `@page margin 0`. Этикетки термопринтера `@page 112mm 75mm`, высота блока 72 мм, иначе появляются пустые страницы. Бланк инвентаризации A4 с полями 12 мм.

### Папки
- `app/` — программа. `Резервные копии/` — JSON-копии данных (**персональные данные клиентов, в git и в облако не класть**). `Исходные данные/` — выгрузка из 1С. `Макеты/` — старые макеты.
- `_разработка/` — исходники модулей (views_*.js, inst.js, pack.js, stock.js, reports.js, inv.js, assistant.js, range.js), сплайс- и патч-скрипты (splice_*.py, patch_*.py), снимки экрана (screenshot.py), тесты печати (printtest_app.py, labels_print_test.py, invprint_test.py — Edge headless `--print-to-pdf` + pymupdf).
- `_разработка/тесты/` — 26 автотестов на jsdom (*_test.js). Запуск описан в «КАК ЗАПУСТИТЬ ТЕСТЫ.txt»: `npm init -y; npm install jsdom@24.1.0`, затем `node имя_test.js`. Тест встраивает скрипты в HTML, url `http://localhost/`.

### Как вносить правки
1. Правь `app/app.js` и `app/styles.css` прямо. Крупные модули удобно писать в `_разработка/` и вклеивать скриптом.
2. После правки запусти `node --check app/app.js`, затем профильный тест и регрессию (все *_test.js). Устаревший тест обнови, удалять нельзя.
2а. **После каждой правки меняй номер версии** `?v=...` у трёх ссылок в `LIVARO.html` (styles.css, catalog-1c.js, app.js), иначе браузер покажет старую версию из кэша. Тесты и .py-скрипты номер версии отрезают сами.
3. Печать проверяй через PDF (Edge headless), внешний вид — через screenshot.py.
4. Windows: PowerShell ломает кавычки во встроенном Python и `node -e`, поэтому пиши скрипты файлами. Консоль работает в CP1251, ставь `PYTHONIOENCODING=utf-8` или выводи в файл.

## Бизнес-правила (важно, не нарушать)
- Единый баланс клиента. В интерфейсе **нет слова «аванс»**: пишем «на балансе X ₽» / «долг X ₽», в печати «НА БАЛАНСЕ».
- Схемы оплаты: крупная предоплата; «купил — перевёл»; оплата сразу; деньги через **водителя клиента** (pending до «Получено»). Своих водителей нет, **водителя в накладной не указывать**.
- Оплата **товаром** (ткань, скотч, механизмы): цену называет клиент («120 м по 165»), а сумму программа проверяет, потому что клиенты ошибаются в умножении. Если товар есть в каталоге, его можно оприходовать на склад.
- Шкафы модульные, собираются как группы в 1С: корпус → двери своего семейства → ручки → карниз → допы. Шкаф в накладной = группа с названием и суммой, состав ниже. Цена 0 = «входит». Ручки до 30 см входят в цену, длиннее — доплата. Ручек столько же, сколько дверей. Ящики и антресоли — доплата. Индивидуальные цены вбиваются вручную, скидку в печати НЕ показывать.
- Пользователь отверг «готовые шкафы» и пошаговый конструктор. Нужно как в 1С: папки + выбор товаров.
- Печать: шапка только «LIVARO» (без адреса, ИНН и логотипа). В накладной есть блок «Состояние расчётов» (баланс до и после). Заказ должен помещаться на 1 лист A4.
- **Порядок цветов** всегда: БЕЛЫЙ, СЕРЫЙ, ВАНИЛЬ, ЛИНО, ВОТАН, далее сатин (константа COLORS, orderIdx при показе).
- Упаковка: двери, рамки со стеклом и фасады кладутся по 2 в коробку + ХРУПКОЕ, зеркала по 1. Нечётная дверь: по умолчанию 3 в одну коробку (настройка oddDoor). Ручки, карниз и фурнитура идут общим пакетом шкафа. Термопринтер печатает наклейки 11,2 × 7,5 см. Дизайн наклейки — **вариант № 8** (выбран 24.10): чёрная полоса слева с вертикальным LIVARO, «Заказ № N» + дата, клиент, «N. Шкаф …», товар, внизу ХРУПКОЕ в рамке и «МЕСТО n / m» (номер внутри шкафа, без «шкаф 1 из 4»). Всё чисто чёрное и жирное.
- **Рассрочка** (розница): номер Р-N, до 4 месяцев, % переплаты. **В накладной покупателя процента нет** (суммы уже с наценкой). Рассрочка ведётся отдельно от балансов оптовиков.
- «Корзина» = корзина заказа. Удалённое лежит в разделе **«Удалённые»** (восстанавливается по категориям).
- «Помощник» в корзине — это правила (assistant.js), не нейросеть.

## План онлайн (утверждён в общих чертах 24.10.2026, документ «План развития LIVARO.html»)
Цель: доступ из любого места (в том числе с телефона начальника), несколько сотрудников с ролями, журнал изменений, ночные копии.
Технический план (предложение Claude, детали согласовать с пользователем):
- **Хостинг только в РФ** (152-ФЗ: в базе ФИО и телефоны клиентов): Timeweb Cloud / Selectel / Яндекс Облако, VPS 2 vCPU / 4 ГБ. Railway (опыт пользователя по другим проектам) здесь НЕ подходит: зарубежный хостинг + закон.
- Стек: **Node.js (Fastify) + PostgreSQL**, Docker Compose (app + postgres + Caddy для HTTPS). Фронтенд оставить текущий: сервер отдаёт те же `LIVARO.html` и `app/`.
- Данные: таблицы по коллекциям (clients, orders, payments, installments, stock_moves, templates, trash) со строками JSONB + `version` (оптимистичная блокировка: при конфликте предупредить и перечитать). Каталог и настройки хранить отдельными документами. На клиенте `load()/save()` заменить синхронизацией изменённых записей через API, расчёты (balance, payMap, склад) пока оставить на клиенте.
- Таблица `audit_log` (кто, когда, что: было → стало). `users` (логин, хеш argon2, роль, активен). Сессии в httpOnly cookie, лимит попыток входа.
- Роли: руководитель, бухгалтер, менеджер продаж, склад (матрица в плане, раздел 3). Права проверять **на сервере**, не только скрывать кнопки.
- Ночной `pg_dump` в S3-хранилище (хранить 30+ дней) и проверка восстановления. Перенос данных: импорт текущей JSON-копии одной кнопкой.
- Этапы: 0 подготовка (git, сервер, домен) → 1 онлайн-версия (3–4 недели) → 2 параллельная работа неделю → переход.
- Развитие потом: акт сверки, напоминания должникам, Telegram-уведомления начальнику, массовые цены → расходы, касса, прибыль, себестоимость → план цеха, статусы готовности, закупки → фото бланка через Claude API (~5–10 ₽ за фото), банковская выписка, кабинет оптовика, QR на этикетках.
- Для Claude API: модель по умолчанию `claude-opus-5-5`. Ключ держит только пользователь, с лимитом расходов, и **ключ не должен попадать во фронтенд** (в онлайн-версии вызывать с сервера).
